# Agent Note：mux 下行溢出时上报缺口，而不是静默丢帧

状态：已实施

[English](2026-08-30-mux-downlink-overflow-resync.md) | 中文

## 问题

每条 mux 下行都持有一个有界的 `FrameQueue`（`DEFAULT_MAX_QUEUED_FRAMES`，10,000 帧），使停滞或缓慢的 Consumer 不会让宿主内存无界增长。达到上限时，队列丢弃最旧的一帧未投递帧并累加 `dropped` 计数，而这个计数从来没有人读：没有帧携带它，没有 RPC 暴露它，也没有日志报告它。因此，消费速度慢于宿主事件速率的客户端会丢失会话事件，且完全得不到任何信号。它的连接保持打开且健康，所以现有的恢复路径一条都不会触发——重连重建由 `onConnected` 驱动，而这里根本没有重连。窗口继续渲染缺口出现时它手上的内容，并一直错下去，直到用户刷新，或传输因无关原因恰好失败。实时视图中的静默陈旧比一次可见的断连更糟，因为没有任何东西告诉用户视图已经不再跟踪该会话。

## 决策

队列自己上报自己的缺口。`FrameQueue` 接受一个可选的 `overflowFrame(dropped)` 工厂；每次丢弃都用累计 `dropped` 总数铸造一个标记帧，`iterate` 会在那些于缺口中幸存下来的帧之前把该标记产出。mux 下行提供这个工厂，铸造 `session/resync` 帧。

标记帧保存在 `pendingOverflow` 字段中，位于环形缓冲之外，不占用槽位。这正是该设计的要点，而非实现上的便利：存放*在*队列里的标记会位于队首，而队首恰好是下一次丢弃所针对的位置，于是报告丢失的那一帧会成为继续丢失的第一个牺牲品。放在外部还意味着永远不必为容纳它而突破上限；投递前的又一次丢弃只会替换掉待投递的标记，使计数保持最新。标记在投递后重新武装，因此之后的每次缺口都会再次上报。

`session/resync` 以连接为作用域，不携带 `sessionId`。队列复用所有已挂载会话，并按年龄丢弃而不读取所丢内容，因此哪些会话丢了事件无法恢复；`dropped` 仅供诊断，客户端无法据一个计数做对账。客户端的应答方式是按历史重建每一个常驻视图——列表与目录 baseline，以及每个已打开的窗口——这正是重连已经在做的事。因此 `SessionManager.handleConnected` 与这个新帧共用一个私有的 `resyncAll()`，因为二者含义相同：该流已经不能再被信任为携带了每一个事件。

宿主（host）下行队列不传入工厂，仍然静默丢弃。它的帧是整份快照，下一次变更会重新发送，因此那里的缺口不会像漏掉 `session/event` 那样把某个视图搁浅。

## 备选方案

**溢出时结束该流（强制重连）。** 已否决。它复用现有的重连恢复且不新增线路表层，但它把一次可恢复的缺口变成一次可见的断连：客户端拆掉两条流、退避、重跑就绪握手，并为每个会话重放每一份 baseline——远超该缺口所需的工作量，而且是用户看得见的 UI 状态跳变。它还有重连循环的风险，因为一个慢到会溢出一次的 Consumer，在更重的重连后重放中会再次溢出。

**给标记帧一个队列槽位。** 基于上文理由否决：位于队首时它就是下一个被丢的帧，因此在持续溢出下标记会被反复丢弃与重铸，可能永远到不了 Consumer。改为为它预留容量则引入上限算术，并在 `maxFrames` 很小时退化。

**按会话发送 resync 帧。** 已否决：队列并不知道被丢弃的帧属于哪些会话，因此要产出按会话的标记就得在丢弃路径上检查帧内容，而且对同一轮突发中更早被丢帧的会话仍然是错的。

**让标记携带 `since` 以做增量续传。** 在此处否决为不成立。宿主的 `since` 游标是 mux 打开时的参数，而这次恢复并不重开流；客户端自己的按会话游标就是它即将重建的那个历史窗口。计数无法替代游标，因此诚实的信号是「你的视图不完整」，而不是「从 N 继续」。

## 影响

慢客户端现在能自行恢复到正确视图，无需刷新，也不必断开连接。代价是 `MuxFrame` 联合中多一个帧及其 zod 分支，外加一条给出丢弃总数以便诊断的 `console.warn`。`dropped` 作为诊断值仍是近似的——它是投递时的总数，既非按会话也非按缺口——这可以接受，因为没有任何客户端决策依赖它的取值。

恢复效果取决于客户端的历史重建：从未打开过的会话没有窗口可重建，被正确地放着不动；projection／queue／jobs 镜像则在随后的 `session/subscribed` 帧上重新取基线。忽略该帧的客户端，处境不会比本次改动之前更差。

## 测试

`frame-queue.spec.ts` 覆盖队列机制：标记先于幸存帧、它能在会丢掉占槽标记的持续溢出中存活、投递后重新武装，以及没有工厂的队列仍然静默丢弃。`mux-overflow.spec.ts` 驱动真实 mux 流越过上限，断言 `session/resync` 是出队的第一帧，这同时也覆盖了接线。`manager.client.spec.ts` 断言该帧触发与重连相同的列表刷新与历史重拉。`rpc-schemas.spec.ts` 覆盖线路分支，包括拒绝非正数的 `dropped`。
