# Agent Note: 搜索索引重建时的逐会话结算

Status: implemented

[English](2026-09-16-session-search-per-item-settlement.md) | 中文

## 问题

SQLite 会话搜索索引在“整批原子”的假设下重建语料。观测完每一个持久化会话之后，重建会再次列出语料，只要任何单个会话的 revision 与已观测的不一致，就丢弃整次尝试（`samePersistenceSnapshots`）。允许两次尝试；第三次失败以 `SESSION_QUERY_PERSISTENCE_FAILED` 暴露，搜索工具把它报告为历史存储不可用。

只要有任何会话的写入速度快于一次观测遍历，这个检查就永远无法通过，因此该失败在正常工作的机器上是必现的，而不是偶发。搜索方自己就是抖动源，因为一次工具调用会追加到它自己的日志。在同一台主机、402 个日志的语料上实测：未修改的构建两次尝试共耗 464 秒后拒绝；索引已经建热也没有帮助，因为该检查比对的是语料的全部条目，而不是某次尝试读过的条目。

## 决定

重建改为逐个会话独立结算。已归档的[统一 session-query 服务](2026-07-23-unified-session-query-service.md) 拥有服务边界与派生索引模型；本 note 只改变一次观测遍历如何对待单个会话的不稳定。

- `touchEntry` 观测单个条目，跳过缓存命中与会话活跃方遮蔽的项。初始遍历与每一轮 top-up 都调用它，因此两者对同一会话适用相同规则，无论该会话何时被发现。
- 读取抛出 `SessionFormatUnsupportedError` 时，把该会话移出语料而不是让观测失败；原始日志保持不动，其余每个兼容会话照常入索引。
- 两次列目录之间出现的会话被吸收进同一次尝试而非推迟，并由 `MAX_TOPUP_ROUNDS` 限定。持续到来的会话无法把循环拖过该预算；预算用尽时会再列一次目录，为漂移检查提供用于比对的快照，因此不会出现条目与自己比对的情况。该次列表还可能揭示本次尝试从未观测过的会话；把它们记为存在而不去读取，可避免把确实存在的会话读成已消失，并像缓存命中一样留给下一次观测。
- 已观测的条目仅在其 revision 与 header 仍与最新列表一致时保留。持续变化的会话单独推迟：丢弃它的 loaded 结果，使重建既不写也不删它的行，保留后端已为它索引的内容。已观测但不在最新列表中的会话确已消失，予以删除。
- 移除 `samePersistenceSnapshots` 及其守护的整语料丢弃。
- `Config.backgroundWarmUp` 在持久化服务接入后构建一次索引，使首次冷建不必塞进某次搜索的 `searchTimeoutMs`。它是尽力而为的，并通过既有队列与搜索串行化：预热期间发起的搜索会等它，而不是与它竞争；等不到自己截止时间的搜索仍然失败。

推迟是自愈的：下一次观测会按推迟会话当时的 revision 重新读取，因此最终稳定下来的会话无需人工干预即可入索引。

## 证据

- `session-query-sqlite` 单测：77/77，且逐文件语句、分支、函数、行覆盖均为 100%。推迟测试先索引一个会话，再让它抖动，然后断言它先前的文本仍能被搜到 —— 把推迟换成删除会让该测试失败。
- 真实语料，同一主机、同一批 402 个日志，包全部取自候选槽位：未修改的构建 464 秒后以 `session-search persistence observation did not stabilize after one retry` 拒绝；修复后的构建 222 秒完成并返回 20 条命中。
- 经完整入口的端到端：用补丁槽位起的 web 实例，在备用端口上针对克隆的状态 home 运行，侧栏一次查询即返回内容命中，片段取自会话正文。

## 考虑过的替代方案

- 提高重试次数。否决：只要有会话写入快于一次遍历，任何次数下该检查都无法通过，而每次都要付整轮读取的代价。
- 把活跃会话排除出漂移检查。否决：这只缩小窗口，没有移除假设，因为由其他进程拥有的会话仍会让整批失败。
- 调大工具的 `searchTimeoutMs`。否决：那改变的是截止时间而非原子性，而且预算是调用方的约定。
- 每次搜索都丢弃派生索引重建。否决：每次都付整轮读取，而且仍会在同样的抖动上失败。

## 后果

- 始终无法稳定的会话在稳定之前不出现在搜索结果里；它已建好的索引行被保留而非删除。
- `SESSION_QUERY_PERSISTENCE_FAILED` 仍然覆盖活跃集合重试，后者依旧是整语料重试，因此调用方还不能把它当作纯存储故障。
- 冷建仍需完整读取语料一次。希望把这份代价记在激活而非某次搜索上的部署可开启 `backgroundWarmUp`。
